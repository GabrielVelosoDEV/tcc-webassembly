    Resumo

    A execução de jogos complexos em navegadores, historicamente dependente de plug-ins proprietários, passou a ser viável com tecnologias padronizadas como o WebAssembly (Wasm), o WebGL e, mais recentemente, o WebGPU. Este trabalho investiga em que medida o WebAssembly, combinado com técnicas de compilação, compressão e distribuição de conteúdo, pode viabilizar a execução de jogos diretamente no navegador, reduzindo barreiras de instalação, compatibilidade e acesso sem comprometer excessivamente o desempenho e a experiência do usuário. Adota-se uma pesquisa bibliográfica e documental, de abordagem analítica e comparativa, fundamentada em especificações oficiais (W3C, IETF, Khronos), documentação técnica de navegadores e cadeias de compilação (LLVM, Emscripten, Rust) e estudos empíricos revisados por pares. Complementarmente, propõe-se um protocolo experimental reproduzível — com código-fonte, variáveis controladas e procedimento estatístico — para comparar versões JavaScript e WebAssembly de uma mesma carga de trabalho e o efeito da distribuição sem compressão, com gzip e com Brotli. Os resultados da revisão indicam que o desempenho do Wasm pode aproximar-se do código nativo em cargas computacionais específicas, mas com diferenças mensuráveis e dependentes do tipo de tarefa, do navegador e do custo de interoperabilidade; que o WebAssembly não comprime automaticamente os recursos de um jogo, sendo o tamanho transferido determinado principalmente pelos formatos dos ativos e pela codificação HTTP; e que o tempo até a interação depende da soma de transferência, compilação, inicialização e carregamento de recursos. Conclui-se que o WebAssembly é condição necessária, mas não suficiente, para a democratização dos jogos no navegador, cuja viabilidade resulta da integração entre compiladores, formatos binários, protocolos de rede, compressão e APIs gráficas.

    Palavras-chave: WebAssembly. Jogos no navegador. Compressão de dados. Desempenho computacional. Distribuição de conteúdo.

    Abstract

    Running complex games in web browsers, historically dependent on proprietary plug-ins, has become feasible through standardized technologies such as WebAssembly (Wasm), WebGL and, more recently, WebGPU. This work investigates to what extent WebAssembly, combined with compilation, compression and content-delivery techniques, can enable games to run directly in the browser, lowering installation, compatibility and access barriers without excessively compromising performance and user experience. The study adopts bibliographic and documentary research with an analytical and comparative approach, grounded in official specifications (W3C, IETF, Khronos), technical documentation of browsers and toolchains (LLVM, Emscripten, Rust), and peer-reviewed empirical studies. In addition, it proposes a reproducible experimental protocol — with source code, controlled variables and a statistical procedure — to compare JavaScript and WebAssembly versions of the same workload and the effect of serving files uncompressed, with gzip and with Brotli. The review indicates that Wasm performance can approach native code for specific computational workloads, but with measurable differences that depend on the task, the browser and interoperability costs; that WebAssembly does not automatically compress a game's assets, the transferred size being determined mainly by asset formats and HTTP content encoding; and that time-to-interaction depends on the sum of transfer, compilation, initialization and asset loading. It concludes that WebAssembly is a necessary but not sufficient condition for democratizing browser games, whose feasibility results from the integration of compilers, binary formats, network protocols, compression and graphics APIs.

    Keywords: WebAssembly. Browser games. Data compression. Computational performance. Content delivery.

          1.1Contextualização: da página estática ao jogo instantâneo

          A World Wide Web foi concebida como um sistema de documentos hipertextuais, e não como uma plataforma de execução de software interativo de alto desempenho. Durante a década de 1990 e boa parte dos anos 2000, a solução encontrada pela indústria para levar programas interativos ao navegador foi delegar a execução a componentes externos — os plug-ins. Applets Java, controles ActiveX, Shockwave e, sobretudo, o Adobe Flash Player permitiram a popularização de jogos casuais acessados por um endereço web, criando um ecossistema inteiro de portais de jogos. Esses componentes, contudo, eram instalados separadamente, executavam código fora do modelo de segurança do navegador e dependiam do suporte de um único fornecedor por plataforma. A Adobe encerrou oficialmente o suporte ao Flash Player em 31 de dezembro de 2020 (ADOBE, 2020), consolidando o fim dessa era.

          Paralelamente, o próprio navegador ganhava capacidades. O elemento <canvas> do HTML, a evolução dos motores JavaScript com compilação just-in-time (JIT) e a especificação WebGL — que expõe ao JavaScript uma API derivada do OpenGL ES (KHRONOS GROUP, 2017) — tornaram possível desenhar gráficos acelerados por GPU sem plug-ins. Ainda assim, motores de jogos profissionais são escritos majoritariamente em C e C++, e reescrevê-los em JavaScript seria economicamente inviável. Surgiram então abordagens para compilar esse código para o navegador: o Emscripten, que traduz a representação intermediária do LLVM para JavaScript (ZAKAI, 2011); o asm.js, um subconjunto estrito e otimizável de JavaScript (HERMAN; WAGNER; ZAKAI, 2014); e o Native Client (NaCl/PNaCl) da Google. Haas et al. (2017) descrevem essas iniciativas como antecessoras diretas do WebAssembly: cada uma resolvia parte do problema, mas nenhuma reunia, ao mesmo tempo, portabilidade entre navegadores, segurança verificável, formato compacto e desempenho previsível.

          O WebAssembly (Wasm) foi projetado em conjunto pelos principais fornecedores de navegadores para preencher essa lacuna. Trata-se de um formato de instruções binário para uma máquina virtual baseada em pilha, pensado como alvo de compilação portátil para linguagens como C, C++ e Rust (HAAS et al., 2017; W3C, 2019a). Sua primeira versão tornou-se Recomendação do W3C em dezembro de 2019, e a versão 3.0 da especificação foi declarada concluída em setembro de 2025, incorporando endereçamento de 64 bits, múltiplas memórias, coleta de lixo, chamadas de cauda e tratamento de exceções (ROSSBERG, 2025). No mesmo período, a API gráfica WebGPU passou a ser suportada oficialmente nos quatro principais navegadores — Chrome, Edge, Firefox e Safari —, ainda que com cobertura de sistemas operacionais em expansão (BEAUFORT, 2025).

          1.2A “magia programacional” como metáfora

          Para um usuário comum, a experiência é desconcertante: um motor de física escrito em C++, um emulador de console ou um jogo 3D completo começam a funcionar segundos depois de se clicar em um link, sem instalador, sem permissões de administrador e sem distinção entre Windows, macOS, Linux ou ChromeOS. É natural descrever esse efeito como uma espécie de magia programacional. Neste trabalho, a expressão é usada deliberadamente como metáfora pedagógica, e não como afirmação científica. A tese defendida é exatamente a oposta: a aparência de mágica resulta de uma cadeia longa, verificável e cheia de compromissos de engenharia — compiladores que traduzem código para uma representação portátil, um formato binário projetado para ser validado em uma passagem, navegadores que compilam esse binário para o processador local enquanto ele ainda está sendo baixado, protocolos de rede que negociam compressão, formatos de ativos adequados à GPU e APIs gráficas que expõem o hardware de forma segura.

          A mágica não está no WebAssembly isolado, mas na integração de várias camadas que, juntas, transformam um executável em uma experiência acessível por URL.

          Desmontar essa metáfora camada por camada é também a estratégia expositiva do trabalho: cada capítulo remove um “truque” e mostra o mecanismo real que o sustenta — e, igualmente importante, os custos e as limitações desse mecanismo.

          1.3Justificativa e relevância

          A relevância do tema pode ser sustentada em três dimensões. Na dimensão tecnológica, o WebAssembly tornou-se um alvo de compilação estável e padronizado, presente em todos os navegadores de grande uso, e motores de jogos amplamente utilizados — como Unity e Godot — oferecem exportação para a Web baseada em Wasm (UNITY TECHNOLOGIES, 2026; GODOT ENGINE, 2026). Na dimensão social, a remoção da etapa de instalação reduz barreiras de acesso em contextos como laboratórios escolares com computadores gerenciados, dispositivos de baixo custo ou usuários sem conhecimento técnico para instalar software — um aspecto relevante para a ideia de democratização que dá título ao trabalho. Na dimensão acadêmica, há uma lacuna de síntese: a literatura revisada por pares tende a estudar desempenho de execução (JANGDA et al., 2019; YAN et al., 2021) ou segurança (LEHMANN; KINDER; PRADEL, 2020) de forma isolada, enquanto a viabilidade de um jogo no navegador depende do encadeamento entre compilação, compressão, transferência, inicialização e renderização. Este trabalho busca justamente articular essas etapas em um modelo único de análise.

          Capítulo 2

          Fundamentos técnicos

          Antes de entender o WebAssembly, é preciso entender o ambiente que o recebe: um navegador multiprocesso, um motor JavaScript especulativo e um processador que só entende código de máquina.

          Pontos-chave do capítulo
          • Navegadores modernos isolam conteúdo em processos com privilégios reduzidos; o código da página nunca fala diretamente com o sistema operacional.
          • JavaScript é rápido graças à especulação do JIT — o que torna seu desempenho dependente de padrões de tipo observados em execução.
          • Wasm já chega tipado e validável: o navegador pode compilá-lo cedo, sem especular sobre tipos.
          • A memória linear é um vetor contíguo de bytes, com acessos verificados — simples, previsível e isolada do restante do processo.

          2.1Arquitetura dos navegadores modernos

          Um navegador contemporâneo é, na prática, um sistema operacional em miniatura. Em vez de um único programa monolítico, os principais navegadores adotam arquiteturas multiprocesso: um processo principal (browser) coordena a interface e as permissões; processos de renderização executam HTML, CSS, JavaScript e WebAssembly de cada site; um processo de GPU centraliza o acesso ao driver gráfico; e serviços como rede e armazenamento rodam em processos próprios. Os processos de renderização operam em uma sandbox do sistema operacional, com privilégios mínimos. Desde 2018, o Chrome aplica o isolamento por site (Site Isolation), que coloca documentos de sites diferentes em processos distintos — uma medida reforçada como defesa contra ataques de canal lateral do tipo Spectre (REIS; MOSHCHUK; OSKOV, 2019; KOCHER et al., 2019).

          Para o desenvolvimento de jogos, essa arquitetura tem duas consequências diretas. Primeiro, todo acesso a recursos do sistema — arquivos, GPU, áudio, dispositivos de entrada — passa por APIs web mediadas pelo navegador; não há chamadas de sistema diretas. Segundo, comandos gráficos emitidos pelo código da página atravessam uma fronteira entre processos até o processo de GPU, o que introduz validação e sobrecarga que um jogo nativo não teria.

          2.2JavaScript e o motor de execução

          JavaScript, padronizado como ECMAScript (ECMA INTERNATIONAL, 2026), é uma linguagem dinamicamente tipada, com coleta automática de lixo e um modelo de concorrência baseado em laço de eventos (event loop). Cada navegador possui seu motor: V8 (Chrome/Edge), SpiderMonkey (Firefox) e JavaScriptCore (Safari). Como uma variável JavaScript pode conter, em momentos diferentes, um inteiro, um número de ponto flutuante, uma string ou um objeto, o motor não sabe de antemão que instruções de máquina gerar para uma operação como a + b.

          A solução adotada pelos motores modernos é a otimização especulativa: o código é inicialmente interpretado ou compilado de forma simples, enquanto o motor coleta informações sobre os tipos efetivamente observados. Trechos executados com frequência (“quentes”) são recompilados por um compilador otimizador que presume que os tipos continuarão os mesmos, inserindo verificações (guards). Se uma suposição é violada, ocorre uma desotimização e a execução volta a um nível menos otimizado. Esse mecanismo explica por que JavaScript bem comportado pode ser muito rápido, mas também por que seu desempenho pode oscilar: ele depende do histórico de execução, do aquecimento (warm-up) e de pausas do coletor de lixo — este último aspecto especialmente sensível em jogos, nos quais uma pausa de poucos milissegundos pode causar perda de quadros.

          2.3Compilação, interpretação e compilação JIT

          Na terminologia clássica de compiladores (AHO et al., 2008), um compilador traduz um programa de uma linguagem-fonte para uma linguagem-alvo antes da execução, enquanto um interpretador executa diretamente as operações do programa-fonte (ou de uma representação intermediária), instrução a instrução. A compilação JIT (just-in-time) combina as duas abordagens: traduz para código de máquina durante a execução, podendo usar informações dinâmicas indisponíveis a um compilador antecipado (AOT, ahead-of-time).

          O WebAssembly ocupa uma posição particular nesse espectro: ele é produzido por compilação AOT a partir de C, C++ ou Rust, mas o resultado ainda não é código de máquina de nenhuma CPU real. O navegador conclui a tradução localmente. Por o Wasm ser estaticamente tipado, essa etapa final não precisa especular sobre tipos: V8 usa um compilador de base, o Liftoff, para iniciar a execução rapidamente, e recompila funções quentes com o otimizador TurboFan em segundo plano (BACKES, 2018); o Firefox adotou estratégia análoga de compilação em camadas e em streaming, compilando o módulo enquanto os bytes ainda chegam pela rede (CLARK, 2018). Há também abordagens baseadas em interpretação in-place do binário Wasm, estudadas por Titzer (2022) como forma de reduzir o tempo e a memória de inicialização.

          2.4Código-fonte, código intermediário, bytecode e código de máquina

          Para tornar concretos esses níveis de representação, considere uma função em C que soma os elementos de um vetor. O mesmo algoritmo atravessa quatro formas até ser executado:

          // (1) Código-fonte em C
int soma(const int *v, int n) {
  int s = 0;
  for (int i = 0; i < n; i++) s += v[i];  // v aponta para a memória linear
  return s;
}
          ; (2) Representação intermediária do LLVM — trecho simplificado do laço
%ptr = getelementptr i32, ptr %v, i32 %i     ; endereço de v[i]
%x   = load i32, ptr %ptr                ; lê v[i]
%s2  = add i32 %s, %x                      ; s += v[i]
          ;; (3) WebAssembly em formato texto — o "bytecode" portátil, aqui legível
(local.get $s)
(local.get $v) (local.get $i) (i32.const 2) (i32.shl) (i32.add) ;; v + i*4
(i32.load)                                          ;; acesso verificado à memória linear
(i32.add) (local.set $s)
          ; (4) Código de máquina gerado pelo navegador (forma possível, em assembly)
mov  eax, [r15 + rdx*1]   ; r15 = base da memória linear; rdx = endereço Wasm
add  ecx, eax

          A forma (3) é o que de fato trafega pela rede, codificada em binário. A forma (4) nunca sai do computador do usuário: é gerada localmente pelo motor e adaptada ao processador presente. Os trechos (2) a (4) são ilustrativos — a saída real de cada ferramenta depende de versão e opções de compilação —, mas a estrutura em camadas é a descrita pela especificação e pela literatura (LATTNER; ADVE, 2004; WEBASSEMBLY COMMUNITY GROUP, 2025).

          2.5Arquiteturas x86-64 e ARM

          Os computadores pessoais são dominados por duas famílias de conjuntos de instruções. A x86-64, de herança CISC, possui instruções de tamanho variável e 16 registradores de propósito geral; a ARM de 64 bits (AArch64), de filosofia RISC, usa instruções de tamanho fixo e 31 registradores de propósito geral (HENNESSY; PATTERSON, 2017). Celulares, tablets, muitos notebooks recentes e computadores Apple utilizam ARM. Um executável nativo é compilado para uma dessas arquiteturas (e para um sistema operacional específico); distribuir um jogo nativo para todas as combinações exige múltiplos binários.

          O WebAssembly abstrai essa diferença: o mesmo arquivo .wasm é traduzido pelo navegador para o conjunto de instruções local. O custo dessa portabilidade aparece em detalhes de baixo nível. Jangda et al. (2019), analisando o código gerado por Chrome e Firefox, identificaram como fontes de lentidão em relação ao nativo, entre outras, maior pressão sobre registradores, mais instruções executadas e verificações adicionais inseridas pelo motor, como checagens de estouro de pilha e de chamadas indiretas pesquisa anterior.

          2.6A memória linear do WebAssembly

          Programas em C, C++ e Rust trabalham com ponteiros, isto é, endereços numéricos de memória. O WebAssembly oferece a esses programas uma memória linear: um vetor contíguo de bytes, endereçado a partir de zero, cujo tamanho é medido em páginas de 64 KiB e pode crescer em tempo de execução pela instrução memory.grow (WEBASSEMBLY COMMUNITY GROUP, 2025) fato documentado. Todo acesso (i32.load, f64.store etc.) é verificado contra os limites dessa memória; um acesso fora dos limites provoca uma interrupção (trap), e não a leitura de outra região do processo.

          No modelo clássico de 32 bits, a memória linear pode chegar a 4 GiB (65.536 páginas); o V8 passou a permitir esse limite completo em 2020, após anos limitado a 2 GiB (HAAS; KUMMEROW; ZAKAI, 2020). Em hospedeiros de 64 bits, os motores costumam reservar um espaço de endereçamento virtual maior que a memória e usar páginas de guarda do sistema operacional, de modo que muitas verificações de limite são realizadas pelo hardware, sem instruções explícitas. A versão 3.0 da especificação introduziu memórias de 64 bits (memory64), cujo limite teórico é muito maior, embora na Web uma memória de 64 bits esteja limitada a 16 GB (ROSSBERG, 2025).

          2.7Modelo de execução e isolamento

          O WebAssembly é definido como uma máquina de pilha com fluxo de controle estruturado: em vez de saltos arbitrários para endereços, existem blocos, laços e desvios para rótulos que envolvem a instrução. Essa restrição permite que o validador verifique o módulo inteiro em uma única passagem linear, garantindo que cada instrução recebe operandos dos tipos corretos (HAAS et al., 2017). A especificação foi, inclusive, mecanizada e verificada formalmente em assistente de provas, com a demonstração de propriedades de solidez do sistema de tipos (WATT, 2018) pesquisa anterior.

          O isolamento decorre de três propriedades combinadas: (a) o código só acessa sua própria memória linear, tabelas e variáveis globais; (b) a pilha de execução — que contém endereços de retorno — não é endereçável pelo programa, o que impede a sobrescrita direta de endereços de retorno; e (c) o módulo não possui nenhuma capacidade de interagir com o mundo externo, exceto pelas funções que o ambiente hospedeiro decide importar para ele. No navegador, isso significa que um módulo Wasm não pode abrir arquivos, acessar a rede ou desenhar na tela sem passar por funções JavaScript fornecidas explicitamente — que, por sua vez, estão sujeitas a todas as restrições da plataforma web.

          Isolamento não é segurança do programa

          O isolamento protege o hospedeiro contra o módulo, mas não protege o módulo contra si mesmo. Um estouro de buffer em código C continua corrompendo dados dentro da memória linear. Como compiladores mantêm uma “pilha sombra” nessa memória para variáveis cujo endereço é tomado, e como a memória linear não tem regiões somente-leitura, certas classes de ataque podem ser até mais simples do que em binários nativos modernos (LEHMANN; KINDER; PRADEL, 2020). O tema é retomado no Capítulo 8.

          2.8Interoperabilidade entre JavaScript e WebAssembly

          No navegador, o WebAssembly não substitui o JavaScript: ele é carregado, instanciado e chamado a partir do JavaScript, por meio da API JavaScript do Wasm (W3C, 2019b). Um módulo declara importações (funções e objetos que precisa receber) e exportações (funções, memórias e tabelas que oferece). A fronteira entre as duas linguagens tem custo e semântica próprios: na versão inicial, apenas tipos numéricos (i32, i64, f32, f64) atravessavam a fronteira; strings, vetores e objetos precisam ser serializados na memória linear e passados como ponteiro e comprimento. Extensões posteriores (tipos de referência, externref, coleta de lixo e operações embutidas sobre strings JavaScript) ampliaram essas possibilidades (ROSSBERG, 2025).

          // Carregamento e uso de um módulo — compilação em streaming enquanto os bytes chegam
const imports = { env: { log: (x) => console.log('valor:', x) } };
const { instance } = await WebAssembly.instantiateStreaming(
  fetch('soma.wasm'), imports);     // exige Content-Type: application/wasm

const { memory, soma, malloc } = instance.exports;
const n = 1000, ptr = malloc(n * 4);   // reserva espaço no heap do módulo
const v = new Int32Array(memory.buffer, ptr, n);  // "janela" JS sobre a memória linear
v.fill(1);
console.log(soma(ptr, n));               // 1000 — a chamada cruza a fronteira JS→Wasm

          Duas consequências práticas derivam desse modelo. A primeira é que chamadas muito frequentes e granulares entre JavaScript e Wasm — por exemplo, uma chamada por vértice ou por pixel — podem anular o ganho do código compilado; motores de jogos tendem a cruzar a fronteira poucas vezes por quadro, transferindo blocos de dados. A segunda é que ferramentas geram automaticamente o “código de cola” (glue code) em JavaScript: o Emscripten produz um arquivo .js que implementa as importações de que o programa C precisa — como uma emulação de sistema de arquivos e de chamadas POSIX — (EMSCRIPTEN, 2026), e o wasm-bindgen, no ecossistema Rust, gera bindings tipados entre structs Rust e objetos JavaScript (WASM-BINDGEN CONTRIBUTORS, 2026).

          Capítulo 3

          WebAssembly em profundidade

          Um formato binário projetado para ser pequeno, validável em uma passagem e compilável enquanto ainda está sendo baixado.

          Pontos-chave do capítulo
          • Objetivos de projeto: seguro, rápido, portátil e compacto — independente de linguagem, hardware e plataforma.
          • Um módulo é uma sequência de seções tipadas; seus quatro primeiros bytes são sempre 00 61 73 6D (“\0asm”).
          • C/C++ chegam ao Wasm via Clang/LLVM e Emscripten; Rust, via rustc (também LLVM) e wasm-bindgen.
          • “Wasm é sempre mais rápido que JS” é falso como generalização: depende da tarefa, da inicialização, da fronteira e do motor.

          3.1Origem e objetivos de projeto

          O WebAssembly surgiu em 2015 como um esforço conjunto de engenheiros dos quatro grandes motores de navegador, organizado em um Grupo Comunitário do W3C. O artigo de apresentação, publicado no PLDI 2017, enuncia os objetivos do formato: ele deveria ser seguro (código não confiável executado sem risco ao hospedeiro), rápido (próximo do desempenho nativo, com aproveitamento das capacidades comuns do hardware), portátil (independente de linguagem, de arquitetura e de plataforma) e compacto (codificação binária menor que texto, para reduzir tempo de transferência) (HAAS et al., 2017). Diferentemente do NaCl, não depende de um subconjunto de código de máquina específico; diferentemente do asm.js, não precisa ser analisado como texto JavaScript.

          A evolução do padrão ocorre por propostas de extensão que percorrem fases de maturidade até serem incorporadas à especificação. A versão 1.0 (o MVP) tornou-se Recomendação W3C em 2019 (W3C, 2019a). A versão 2.0 incorporou, entre outros, instruções vetoriais SIMD de 128 bits, operações de memória em bloco, múltiplos valores de retorno e tipos de referência. A versão 3.0, concluída em 2025, acrescentou memórias de 64 bits, múltiplas memórias por módulo, coleta de lixo de baixo nível, referências tipadas, chamadas de cauda, tratamento de exceções e SIMD relaxado (ROSSBERG, 2025). Essas adições ampliaram o conjunto de linguagens que compilam de forma eficiente para Wasm — Java, Kotlin, Dart, OCaml e Scheme passaram a ter compiladores que usam a coleta de lixo nativa do formato.

          3.2Formato binário e estrutura de módulos

          A unidade de distribuição é o módulo. Em binário, ele começa com um preâmbulo fixo de 8 bytes — o “número mágico” 00 61 73 6D (os caracteres \0asm) seguido da versão 01 00 00 00 — e continua com uma sequência de seções, cada uma identificada por um byte de identificação e seu tamanho codificado em LEB128 (inteiros de comprimento variável) (WEBASSEMBLY COMMUNITY GROUP, 2025). Essa organização permite que o decodificador processe o arquivo em fluxo, sem precisar do arquivo inteiro para começar.

          3.3Validação, compilação, instanciação e execução

          A API distingue duas entidades. Um WebAssembly.Module é o código validado e compilado, sem estado; ele pode ser armazenado em cache e enviado a Web Workers. Uma WebAssembly.Instance é o módulo vinculado às suas importações, com memória, tabelas e globais alocadas (W3C, 2019b). O ciclo de vida segue quatro etapas:

          1. Decodificação e validação — o motor verifica a boa-formação e a tipagem de todas as funções. Um módulo inválido é rejeitado antes de executar qualquer instrução fato documentado.
          2. Compilação — o código validado é traduzido para a arquitetura local, em uma ou mais camadas (Seção 2.3). Com compileStreaming e instantiateStreaming, essa etapa se sobrepõe à transferência pela rede (W3C, 2019c).
          3. Instanciação — as importações são resolvidas, a memória é alocada, os segmentos de dados e de elementos são copiados e a função start, se houver, é executada.
          4. Execução — o hospedeiro chama funções exportadas. Erros de execução (divisão inteira por zero, acesso fora dos limites, instrução unreachable) resultam em traps, que, no navegador, se manifestam como exceções WebAssembly.RuntimeError.

          Uma consequência importante para jogos é que a validação e a compilação ocorrem no dispositivo do usuário. O custo dessa etapa cresce com o tamanho do código e é maior em dispositivos lentos — razão pela qual os motores investiram em compiladores de base rápidos e em cache do código compilado.

          3.4Importações, exportações e o formato texto

          O formato texto (WAT) é uma representação legível, em expressões-S, do mesmo conteúdo do binário. O módulo de demonstração deste trabalho exporta uma memória e uma função que acumula raízes quadradas — uma carga sintética simples, útil para observar o pipeline, mas não representativa de um jogo:

          (module
  (memory (export "mem") 1)                   ;; 1 página = 64 KiB, visível ao JS
  (func (export "work") (param $n i32) (result f64)
    (local $i i32) (local $acc f64)          ;; locais iniciam em zero
    (block $done
      (loop $next                                ;; fluxo de controle estruturado
        (br_if $done (i32.ge_s (local.get $i) (local.get $n)))
        (local.set $acc (f64.add (local.get $acc)
          (f64.sqrt (f64.convert_i32_s (local.get $i)))))
        (local.set $i (i32.add (local.get $i) (i32.const 1)))
        (br $next)))
    (local.get $acc)))

          Nenhuma importação é declarada: o módulo é, literalmente, incapaz de produzir qualquer efeito fora de sua memória e de seu valor de retorno. Um jogo real importa dezenas ou centenas de funções — para desenhar via WebGL, tocar áudio, ler o teclado, obter o tempo —, todas implementadas no JavaScript de cola.

          3.5De C e C++ para WebAssembly: LLVM e Emscripten

          O LLVM é uma infraestrutura de compilação organizada em torno de uma representação intermediária (IR) em forma SSA, sobre a qual operam otimizações independentes de linguagem e de arquitetura (LATTNER; ADVE, 2004). Essa separação entre front-ends (Clang para C/C++, rustc para Rust) e back-ends (x86-64, AArch64, wasm32) é o que torna o WebAssembly um alvo “natural”: basta um back-end que gere Wasm a partir da IR para que todas as linguagens baseadas em LLVM o alcancem.

          O Emscripten é a cadeia de ferramentas mais madura para C/C++ na Web. Criado originalmente para gerar JavaScript a partir da IR do LLVM (ZAKAI, 2011), hoje usa o back-end Wasm do próprio LLVM e complementa a compilação com: (a) uma biblioteca C padrão e implementações de APIs POSIX sobre recursos da Web; (b) portes de bibliotecas comuns em jogos, como SDL2 e uma camada de OpenGL ES sobre WebGL; (c) um sistema de arquivos virtual; (d) o otimizador wasm-opt, do projeto Binaryen, aplicado ao binário final; e (e) o JavaScript de cola (EMSCRIPTEN, 2026).

          # Compilação típica de um jogo C/C++ com Emscripten (opções documentadas em emscripten.org)
emcc main.c render.c physics.c -o jogo.html \
  -O3 -flto \                     # otimização agressiva + otimização em tempo de ligação
  -sUSE_SDL=2 -sUSE_WEBGL2=1 \    # porte da SDL2 e contexto WebGL 2
  -sALLOW_MEMORY_GROWTH=1 \       # permite memory.grow em vez de memória fixa
  --preload-file assets@/assets   # empacota ativos em jogo.data (sistema de arquivos virtual)
# Saída: jogo.html (página), jogo.js (cola), jogo.wasm (código), jogo.data (ativos)

          Há um ponto de atrito conceitual importante para jogos. Um jogo nativo costuma ter um laço principal infinito (while (rodando) { atualizar(); desenhar(); }). No navegador, um laço que nunca devolve o controle bloqueia a renderização e os eventos da página. O Emscripten resolve isso convertendo o laço em uma função chamada a cada quadro pelo navegador, via emscripten_set_main_loop, que usa internamente requestAnimationFrame (EMSCRIPTEN, 2026). Código que depende de bloqueio (esperar um arquivo, dormir) exige reestruturação ou transformações como o Asyncify, que tem custo em tamanho e velocidade.

          #include <emscripten.h>
static void quadro(void) {        // chamado pelo navegador a cada atualização de tela
  ler_entrada(); atualizar_fisica(); desenhar();
}
int main(void) {
  iniciar_recursos();
  emscripten_set_main_loop(quadro, 0, 1);  // 0 = usar requestAnimationFrame; 1 = simular laço infinito
}

          3.6De Rust para WebAssembly

          O compilador Rust também usa o LLVM e oferece alvos como wasm32-unknown-unknown (sem sistema operacional, típico para a Web) e alvos WASI para execução fora do navegador. O ecossistema provê o wasm-bindgen, que gera bindings entre Rust e JavaScript, e o web-sys, que expõe as APIs web a código Rust (WASM-BINDGEN CONTRIBUTORS, 2026). Como Rust garante segurança de memória em tempo de compilação para código que não usa unsafe, ele mitiga parte das vulnerabilidades discutidas no Capítulo 8 — embora não elimine falhas lógicas nem vulnerabilidades em dependências.

/// Atualiza posições de partículas; o vetor vive na memória linear e é visto pelo JS sem cópia.
#[wasm_bindgen]
pub fn integrar(pos: &mut [f32], vel: &[f32], dt: f32) {
    for (p, v) in pos.iter_mut().zip(vel) { *p += v * dt; }   // sem verificação de nulo; limites checados

          3.7WebAssembly, JavaScript e código nativo: uma comparação sem generalizações

          É comum encontrar a afirmação de que “WebAssembly é mais rápido que JavaScript”. Como generalização, ela é incorreta. A evidência disponível sugere que o resultado depende de pelo menos cinco fatores, explorados no painel interativo abaixo.

          Em relação ao código nativo, a referência empírica mais citada é o estudo de Jangda et al. (2019), que construiu uma infraestrutura para executar programas do SPEC CPU — maiores e mais realistas do que os benchmarks usados em avaliações anteriores — no navegador. Nas versões de Chrome e Firefox avaliadas, os programas em Wasm foram, em média, cerca de 45% (Firefox) e 55% (Chrome) mais lentos do que o nativo, com casos de lentidão de até 2,08× e 2,5×, respectivamente pesquisa anterior. O estudo original de Haas et al. (2017), com o PolyBenchC (núcleos numéricos menores), havia encontrado parte dos programas muito próxima do nativo e quase todos dentro de um fator 2. As duas evidências não se contradizem: indicam que “próximo do nativo” é plausível para núcleos computacionais compactos, mas que aplicações grandes sofrem sobrecargas mensuráveis — e que esses números refletem versões de motores de 2017–2019, que evoluíram desde então.

          Capítulo 4

          Compressão e distribuição de jogos

          O WebAssembly não comprime um jogo. O que chega ao usuário — e quanto tempo leva — é decidido pelos formatos dos ativos, pela codificação HTTP, pelo empacotamento e pelo cache.

          Pontos-chave do capítulo
          • Um jogo web transfere código (.wasm + .js) e, sobretudo, ativos (texturas, modelos, áudio) — cada um com sua técnica de compressão.
          • gzip, Brotli e Zstandard são codificações de transporte sem perdas, negociadas por HTTP; não alteram o arquivo armazenado no cliente.
          • No E1, binários Wasm reais encolheram 51–74% com gzip-9 e 58–81% com Brotli-11.
          • É preciso distinguir três tamanhos: o transferido, o descomprimido e o ocupado em memória (CPU e GPU).
          • Cache com nomes versionados, CDN e carregamento progressivo podem pesar mais na experiência do que o algoritmo de compressão.

          4.1Anatomia do que é transferido

          Quando se diz que um jogo “roda no navegador”, o que efetivamente trafega pela rede é um conjunto heterogêneo de arquivos: a página HTML; o código JavaScript de cola; o módulo .wasm com a lógica do motor e do jogo; um ou mais pacotes de dados (por exemplo, o arquivo .data gerado pelo Emscripten) ou ativos avulsos — texturas, malhas 3D, animações, áudio, vídeo, shaders, fontes e níveis. Em jogos com conteúdo visual rico, a parcela de ativos tende a superar, em muito, a parcela de código interpretação do autor.

          Ponto central

          O WebAssembly é um formato para código. Seu projeto binário é compacto (HAAS et al., 2017), mas ele não comprime texturas, áudio ou modelos, nem aplica, por si só, compressão ao próprio binário durante a transferência. A redução do tamanho transferido depende das técnicas escolhidas para cada tipo de arquivo, do formato dos recursos e da infraestrutura de distribuição.

          4.2Fundamentos: entropia, compressão sem perdas e com perdas

          A teoria da informação de Shannon (1948) estabelece que a quantidade média mínima de bits necessária para representar símbolos de uma fonte é dada por sua entropia:

          H(X) = − Σi p(xi) · log2 p(xi)
          (1)

          em que p(xi) é a probabilidade do símbolo xi. Dados com muita repetição ou distribuição desigual de símbolos têm baixa entropia e comprimem bem; dados quase aleatórios — incluindo dados já comprimidos — não.

          A compressão sem perdas permite reconstruir exatamente os bytes originais; é obrigatória para código executável, dados estruturados e qualquer informação em que um único bit alterado seja inaceitável. Duas famílias de técnicas a sustentam: a substituição de repetições por referências a ocorrências anteriores, introduzida por Ziv e Lempel (1977) (LZ77), e a codificação de entropia, como os códigos de Huffman (1952), que atribui códigos curtos a símbolos frequentes. A compressão com perdas descarta informação considerada pouco perceptível — detalhes de alta frequência em imagens, componentes inaudíveis em áudio — e atinge taxas muito superiores, mas só é aplicável a dados perceptuais (SAYOOD, 2017).

          4.3Compressão de transporte: gzip, Brotli e Zstandard

          No HTTP, o cliente anuncia as codificações que aceita no cabeçalho Accept-Encoding, e o servidor indica a codificação aplicada no cabeçalho Content-Encoding (FIELDING; NOTTINGHAM; RESCHKE, 2022a). O navegador descomprime de forma transparente antes de entregar os bytes à página — e, no caso do Wasm, antes de alimentar o compilador em streaming. Quando há caches intermediários, o cabeçalho Vary: Accept-Encoding é necessário para que variantes diferentes não sejam confundidas.

          • gzip — formato de arquivo que encapsula o algoritmo DEFLATE, combinação de LZ77 (janela de 32 KiB) e códigos de Huffman (DEUTSCH, 1996a; DEUTSCH, 1996b). É universalmente suportado.
          • Brotli — combina uma variante moderna de LZ77, codificação de Huffman de segunda ordem e modelagem de contexto, com janelas de até 16 MiB e um dicionário estático embutido de cerca de 120 KiB, composto de fragmentos comuns de texto e da Web (ALAKUIJALA; SZABADKA, 2016). É suportado por todos os navegadores modernos, mas apenas sob HTTPS.
          • Zstandard (zstd) — algoritmo com codificação de entropia baseada em FSE (Finite State Entropy), registrado como codificação de conteúdo HTTP (COLLET; KUCHERAWY, 2021). Suportado pelo Chrome desde a versão 123 e pelo Firefox desde a 126; o Safari adicionou suporte na versão 26.3, de fevereiro de 2026, quando o recurso passou a ser considerado de disponibilidade básica entre os principais navegadores (WEB PLATFORM DX, 2026).
          • Dicionários compartilhados — a RFC 9842, publicada em 2025, define o transporte de dicionários de compressão por HTTP, permitindo que uma versão anterior de um recurso sirva de dicionário para comprimir a nova versão (codificações dcb e dcz, para Brotli e Zstandard) (MEENAN; WEISS, 2025). Para jogos atualizados com frequência, isso abre a possibilidade de transferir apenas as diferenças entre versões do binário interpretação do autor.

          Há uma decisão de engenharia importante: compressão dinâmica (o servidor comprime a cada requisição, em níveis rápidos) ou pré-compressão estática (os arquivos são comprimidos uma vez, no build, nos níveis máximos). Como os binários de um jogo mudam apenas a cada versão, a pré-compressão permite usar níveis lentos, como Brotli 11, sem custo por requisição. Alguns motores, como o Unity, geram arquivos pré-comprimidos e oferecem um modo de descompressão em JavaScript para servidores que não conseguem enviar o cabeçalho Content-Encoding adequado (UNITY TECHNOLOGIES, 2026); essa alternativa, porém, transfere o trabalho de descompressão para o código da página, perdendo a descompressão nativa e otimizada do navegador interpretação do autor.

          4.4Compressão do executável versus compressão dos recursos

          Binários Wasm são bons candidatos à compressão sem perdas: contêm opcodes recorrentes, sequências de instruções repetidas entre funções, tabelas e strings. Para quantificar esse efeito em artefatos reais, este trabalho executou o Experimento E1 (descrito em detalhe na Seção 7.2), que aplicou gzip, Brotli e Zstandard a sete binários Wasm de bibliotecas utilizadas em jogos e aplicações interativas. Nos binários avaliados, a redução de tamanho variou de 51,0% a 73,5% com gzip nível 9 e de 57,8% a 80,9% com Brotli nível 11; em todos os casos, Brotli 11 produziu o menor arquivo experimento deste trabalho.

          A situação dos recursos é distinta. Imagens JPEG ou PNG, áudio Opus ou Vorbis e vídeos já são armazenados em formatos comprimidos; aplicar gzip ou Brotli sobre eles produz ganho marginal, porque sua entropia já é alta (Equação 1). Por isso, a compressão eficaz de ativos acontece no formato, durante o build, e não na camada HTTP — e, ao contrário do código, ela costuma envolver perdas controladas.

          4.5Compressão de texturas, modelos, áudio e vídeo

          Texturas

          Formatos como PNG e JPEG são eficientes para transferência, mas a GPU não os entende: antes do envio à placa de vídeo, a imagem precisa ser decodificada para pixels brutos (por exemplo, RGBA de 8 bits por canal, 4 bytes por pixel). As GPUs suportam, em vez disso, formatos de compressão de textura em bloco — famílias BCn (comuns em desktop), ETC2 e ASTC (comuns em dispositivos móveis) — que permanecem comprimidos na memória de vídeo e são decodificados pelo próprio hardware durante a amostragem. O problema para a Web é que não há um formato de bloco suportado por todas as GPUs. O contêiner KTX 2.0, do Khronos Group, combinado com a supercompressão Basis Universal, resolve isso armazenando uma representação intermediária que é transcodificada no cliente para o formato que a GPU local suporta (KHRONOS GROUP, 2026a; BINOMIAL, 2026). Não por acaso, o transcodificador Basis distribuído com a biblioteca three.js é, ele próprio, um módulo WebAssembly — um dos binários avaliados no E1.

          Modelos 3D

          O formato glTF 2.0, especificado pelo Khronos Group, foi concebido para transmissão e carregamento eficientes de cenas 3D, separando a descrição da cena (JSON) dos buffers binários de geometria (KHRONOS GROUP, 2021). A geometria pode ser ainda comprimida com o Draco, biblioteca da Google que aplica quantização e codificação preditiva a malhas (GOOGLE, 2026) — com perda controlada de precisão nas coordenadas. O decodificador Draco também é distribuído como Wasm, e também foi avaliado no E1.

          Áudio e vídeo

          Codecs perceptuais como o Opus (VALIN; VOS; TERRIBERRY, 2012) reduzem drasticamente o tamanho de músicas e efeitos sonoros. Há, contudo, um custo de memória frequentemente negligenciado: a API Web Audio decodifica o arquivo inteiro para amostras PCM em ponto flutuante de 32 bits ao usar decodeAudioData (W3C, 2021). Músicas longas costumam ser reproduzidas por streaming (por exemplo, com o elemento <audio>), enquanto efeitos curtos são decodificados por completo para baixa latência. Vídeos (cinemáticas) seguem lógica semelhante, com decodificação geralmente acelerada por hardware.

          4.6Tamanho transferido, tamanho descomprimido e memória ocupada

          Um erro comum é tratar o tamanho do download como medida única do “peso” de um jogo. É mais preciso distinguir três grandezas, que as próprias APIs do navegador expõem parcialmente — a Resource Timing API informa transferSize, encodedBodySize e decodedBodySize de cada recurso:

          1. Tamanho transferido (St): bytes que atravessam a rede, após a codificação HTTP. Determina o tempo de download e o custo de banda.
          2. Tamanho descomprimido (Sd): bytes após a descompressão HTTP — o arquivo “como armazenado”. Determina, por exemplo, o trabalho do compilador Wasm.
          3. Memória ocupada (M): o que o recurso ocupa após ser decodificado e preparado para uso, na RAM e na memória de vídeo. Pode ser várias vezes maior que Sd.

          Para uma textura não comprimida em bloco, a memória ocupada pode ser estimada por:

          Mtex ≈ w · h · b · 43
          (2)

          em que w e h são as dimensões em pixels, b é o número de bytes por pixel e o fator 4/3 aproxima o acréscimo da cadeia de mipmaps (série geométrica 1 + ¼ + 1/16 + … → 4/3).

          Exemplo didático hipotético

          Considere uma textura de 2048 × 2048 pixels. Em RGBA8 (b = 4), ocupa 2048 · 2048 · 4 = 16.777.216 bytes (16 MiB) sem mipmaps e cerca de 21,3 MiB com eles — independentemente de o arquivo PNG transferido ter, digamos, 3 MiB. Em um formato de bloco como BC7 ou ASTC 4×4 (1 byte por pixel), a mesma textura ocupa 4 MiB (≈ 5,3 MiB com mipmaps): quatro vezes menos memória de vídeo. Para o áudio, 3 minutos de música estéreo a 48 kHz decodificados para float32 ocupam 180 · 48.000 · 2 · 4 = 69.120.000 bytes (≈ 65,9 MiB), ainda que o arquivo Opus correspondente seja muito menor. Os valores derivam apenas de aritmética sobre parâmetros assumidos; não são medições.

          A consequência para jogos no navegador é direta: um projeto pode ter download modesto e, ainda assim, esgotar a memória de um celular de entrada, sobretudo porque o navegador impõe limites próprios a cada aba e à memória linear (Seção 2.6).

          4.7Empacotamento de arquivos e sistemas de arquivos virtuais

          Código C/C++ legado espera ler arquivos com fopen. Como o navegador não oferece acesso direto ao sistema de arquivos do usuário, o Emscripten implementa um sistema de arquivos virtual: com --preload-file, os ativos são empacotados em um arquivo .data, baixado antes de main() e montado em memória (MEMFS); com --embed-file, são embutidos no próprio binário; o IDBFS persiste arquivos no IndexedDB; e há suporte a carregamento sob demanda (EMSCRIPTEN, 2026). A plataforma web oferece ainda o Origin Private File System (OPFS), definido pelo padrão File System do WHATWG, com acesso eficiente a arquivos privados da origem (WHATWG, 2026b).

          O empacotamento envolve compromissos. Um pacote monolítico reduz o número de requisições e comprime melhor (o compressor encontra mais redundância), mas obriga o download integral antes do início e invalida todo o cache a cada alteração. Muitos arquivos pequenos permitem carregamento granular e cache seletivo; com HTTP/2 e HTTP/3, que multiplexam requisições em uma única conexão (BISHOP, 2022), o custo por requisição diminuiu, tornando a fragmentação mais atrativa do que era no HTTP/1.1 interpretação do autor.

          4.8Download integral versus carregamento progressivo

          No modelo de download integral, o jogo só se torna interativo após receber todo o código e todos os ativos. É simples de implementar e adequado a jogos pequenos. No modelo progressivo, divide-se o conteúdo em um caminho crítico — o mínimo para exibir menu e primeira cena — e em conteúdo diferido, baixado em segundo plano ou sob demanda (níveis seguintes, texturas de alta resolução, idiomas). Três mecanismos sustentam o carregamento progressivo: (a) a compilação em streaming do Wasm, que sobrepõe transferência e compilação (CLARK, 2018); (b) a separação dos ativos em pacotes por nível ou por cena; e (c) a substituição gradual de recursos de baixa resolução por versões de alta resolução. A experiência percebida depende mais do tamanho do caminho crítico do que do tamanho total do jogo interpretação do autor.

          4.9Cache do navegador, CDN e estratégias de invalidação

          O cache HTTP é governado por cabeçalhos como Cache-Control e por validadores como ETag (FIELDING; NOTTINGHAM; RESCHKE, 2022b). Para ativos de jogos, uma estratégia robusta é o versionamento por conteúdo: o nome do arquivo inclui um hash do seu conteúdo (por exemplo, jogo.3f9a2c.wasm) e é servido com Cache-Control: max-age=31536000, immutable. Quando o conteúdo muda, muda o nome — e a página HTML, servida com validação a cada acesso, passa a referenciar o novo arquivo. A invalidação torna-se, assim, implícita e precisa.

          Uma CDN (Content Delivery Network) replica esses arquivos em servidores de borda geograficamente próximos do usuário, reduzindo o tempo de ida e volta (RTT) e a carga sobre o servidor de origem (GRIGORIK, 2013). Além do cache HTTP, Service Workers permitem armazenar o jogo inteiro na Cache API e servi-lo sem rede, aproximando a experiência de uma aplicação instalada (W3C, 2026b). Os motores de navegador também podem armazenar em cache o código de máquina compilado de módulos Wasm, evitando recompilação em visitas subsequentes — uma otimização dependente de implementação, não garantida pela especificação.

          4.10Modelagem quantitativa da transferência

          Para comparar estratégias, definem-se a taxa de compressão e a redução percentual de tamanho:

          CR = SorigScomp      R(%) = Sorig − ScompSorig · 100
          (3)

          Um modelo simplificado do tempo de transferência de um recurso, desconsiderando o crescimento gradual da janela de congestionamento do TCP/QUIC, perdas de pacotes e paralelismo, é:

          Ttransf ≈ k · RTT + 8 · ScompB
          (4)

          em que RTT é o tempo de ida e volta, k o número de viagens necessárias para estabelecer conexão e requisitar o recurso, Scomp o tamanho transferido em bytes e B a largura de banda em bits por segundo.

          A compressão compensa quando o tempo economizado na rede supera o tempo de descompressão no cliente, Tdesc:

          Tdesc < 8 · (Sorig − Scomp)B
          (5)

          Em redes rápidas e dispositivos lentos, a margem diminui; em redes móveis, a compressão quase sempre compensa. Com descompressão em streaming, parte de Tdesc sobrepõe-se à própria transferência.

          Capítulo 5

          Arquitetura de um jogo executado no navegador

          Do código-fonte ao primeiro quadro na tela: onze etapas, cinco APIs e uma fronteira que precisa ser atravessada com parcimônia.

          Pontos-chave do capítulo
          • Um jogo web combina: página e cola JS, módulo Wasm, API gráfica (WebGL/WebGPU), áudio, entrada, workers e armazenamento.
          • O ciclo de vida tem onze etapas, distribuídas entre desenvolvedor, rede e cliente — cada uma com custo próprio.
          • O laço principal precisa ceder controle ao navegador a cada quadro (requestAnimationFrame).
          • Threads exigem isolamento de origem cruzada (COOP/COEP), o que tem implicações práticas de hospedagem.

          5.1Visão geral em camadas

          Uma aplicação de jogo baseada em WebAssembly pode ser descrita como uma pilha de quatro camadas. No topo, a página (HTML, CSS e JavaScript de inicialização) cria o <canvas>, exibe a tela de carregamento e captura eventos. Abaixo, o código de cola em JavaScript implementa as importações exigidas pelo módulo e traduz chamadas do motor para as APIs web. A terceira camada é o módulo Wasm, que contém o motor (renderizador, física, áudio lógico, sistema de entidades) e a lógica do jogo. A base é formada pelas APIs da plataforma web, que o navegador implementa sobre o sistema operacional e os drivers.

          5.2O ciclo de vida: do código-fonte ao quadro renderizado

          O fluxo técnico completo pode ser decomposto em onze etapas. Selecione cada etapa no diagrama interativo para ver onde ela ocorre, o que faz e quais custos introduz.

          5.3Papel de cada componente

          JavaScript

          JavaScript é o “sistema operacional” do jogo no navegador: carrega o módulo, fornece suas importações, recebe eventos e é o único caminho até as APIs da plataforma. Em motores portados, seu papel é sobretudo de tradução; em arquiteturas híbridas, pode concentrar interface, rede e lógica de alto nível, deixando ao Wasm os núcleos computacionais.

          WebGL e WebGPU

          O WebGL 2.0 expõe ao JavaScript uma API baseada no OpenGL ES 3.0 e é a base gráfica mais amplamente disponível hoje (KHRONOS GROUP, 2017). O WebGPU é uma API moderna, mais próxima de Vulkan, Metal e Direct3D 12, com objetos de estado pré-validados (pipelines), shaders escritos em WGSL e suporte nativo a compute shaders (W3C, 2026a). Desde o fim de 2025, o WebGPU é suportado oficialmente no Chrome e no Edge (desde a versão 113, em Windows, macOS e ChromeOS, e no Android a partir da 121), no Firefox (Windows a partir da versão 141; macOS em ARM a partir da 145) e no Safari 26 (macOS, iOS, iPadOS e visionOS), com suporte a outras plataformas — como Linux — ainda em andamento (BEAUFORT, 2025). Na prática, motores mantêm WebGL 2 como alternativa de compatibilidade.

          Em ambos os casos, o módulo Wasm não acessa a GPU diretamente: comandos são emitidos via importações JavaScript, validados pelo navegador e encaminhados ao processo de GPU (Figura 2). Essa validação é parte do modelo de segurança e um custo adicional em relação a APIs nativas.

          Web Workers e threads

          Web Workers executam JavaScript (e Wasm) em threads separadas, comunicando-se por troca de mensagens (WHATWG, 2026a). Para que várias threads compartilhem a mesma memória linear — requisito para portar motores multithread em C++ —, é necessário um SharedArrayBuffer e operações atômicas. Após a descoberta do Spectre, navegadores passaram a exigir que a página esteja em estado de isolamento de origem cruzada, obtido com os cabeçalhos Cross-Origin-Opener-Policy: same-origin e Cross-Origin-Embedder-Policy: require-corp (MDN WEB DOCS, 2026a). A experiência do motor Godot ilustra o impacto prático dessa exigência: a versão 4.0 adotou threads por padrão na Web, mas a equipe constatou que as condições impostas aos servidores eram difíceis de cumprir em portais de jogos e conflitavam com integrações de anúncios e pagamentos, o que levou à reintrodução de exportações de thread única no Godot 4.3 (GODOT ENGINE, 2024a; SCOTT, 2024).

          Áudio

          A Web Audio API, Recomendação do W3C, define um grafo de nós de processamento de áudio e o AudioWorklet, que executa código de processamento em uma thread de áudio dedicada (W3C, 2021). Motores que mixam o áudio em software dentro do Wasm dependem de alimentar esse grafo com regularidade; em execução de thread única, quedas de quadro podem provocar falhas audíveis — problema documentado pelo Godot, que passou a usar amostras reproduzidas diretamente pela Web Audio para mitigá-lo (SCOTT, 2024).

          Armazenamento e sistemas de arquivos virtuais

          Jogos precisam persistir progresso, configurações e, eventualmente, ativos baixados. A plataforma oferece IndexedDB (banco de objetos assíncrono), a Cache API (respostas HTTP, usada por Service Workers) e o OPFS (WHATWG, 2026b). Sistemas de arquivos virtuais do Emscripten mapeiam essas APIs para a semântica POSIX esperada pelo código C/C++ (Seção 4.7). O armazenamento é limitado por cotas definidas pelo navegador e pode ser removido pelo usuário ou sob pressão de espaço, o que deve ser considerado no projeto de saves.

          5.4O laço principal e a sincronização com o navegador

          O navegador sinaliza o momento adequado para produzir um novo quadro por meio de requestAnimationFrame, cujo callback é tipicamente invocado na taxa de atualização da tela (WHATWG, 2026a). A cada invocação, o jogo lê a entrada acumulada, avança a simulação (frequentemente com passo fixo, para determinismo da física), emite os comandos de desenho e devolve o controle. Se o trabalho de um quadro exceder o orçamento — 16,67 ms a 60 Hz —, o quadro seguinte é perdido. Há ainda a possibilidade de transferir o canvas para um worker (OffscreenCanvas), liberando a thread principal para a interface da página.

          // Laço de jogo com passo fixo de simulação e renderização sincronizada à tela
const PASSO = 1000 / 60;            // 60 atualizações de física por segundo
let acumulado = 0, anterior = performance.now();
function quadro(agora) {
  acumulado += Math.min(agora - anterior, 250);  // evita "espiral da morte" após pausa
  anterior = agora;
  while (acumulado >= PASSO) { wasm.atualizar(PASSO); acumulado -= PASSO; }  // lógica em Wasm
  wasm.desenhar(acumulado / PASSO);                 // interpolação; emite chamadas WebGL via cola
  requestAnimationFrame(quadro);
}
requestAnimationFrame(quadro);

          Capítulo 6

          Desempenho e otimização

          Desempenho não é um número: é um conjunto de tempos, taxas e distribuições, cada um com seu gargalo e sua métrica adequada.

          Pontos-chave do capítulo
          • Tempo de download ≠ tempo até a interação: este soma conexão, transferência, compilação, instanciação, recursos críticos e o primeiro quadro.
          • FPS médio deve ser calculado a partir do tempo total de quadros; a média de FPS instantâneos superestima o desempenho.
          • Percentis (p95, p99) de tempo de quadro e de latência revelam engasgos que médias escondem.
          • Desempenho próximo ao nativo é possível em núcleos computacionais, mas não garantido em aplicações completas.

          6.1Do clique à interação: decompondo o tempo de carregamento

          Do ponto de vista do jogador, o que importa é o intervalo entre acessar a URL e poder jogar. Esse intervalo — aqui chamado de tempo até a interação (TTTI) — inclui muito mais do que o download. Uma decomposição aproximada, considerando a sobreposição entre transferência e compilação em streaming, é:

          TTTI ≈ Tcon + Tpág + max(Ttransf,wasm, Tcomp) + Tinst + Trec + T1q
          (6)

          em que Tcon é o estabelecimento de conexão (DNS, TCP/QUIC, TLS); Tpág, o carregamento da página e da cola JS; Ttransf,wasm e Tcomp, a transferência e a compilação do módulo (sobrepostas se houver streaming; somadas, caso contrário); Tinst, a instanciação e a inicialização do motor; Trec, o carregamento e o preparo dos recursos críticos (incluindo decodificação de texturas e áudio e compilação de shaders); e T1q, a produção do primeiro quadro interativo.

          Essa decomposição torna evidente por que reduzir apenas o tamanho do binário pode ter efeito limitado: se os recursos críticos dominam, comprimir o .wasm encurta um segmento pequeno da barra. O inverso também ocorre: um binário de dezenas de megabytes pode tornar a compilação dominante em dispositivos lentos, mesmo com rede rápida.

          6.2Tempo de download, de compilação e de inicialização

          O tempo de download depende do tamanho transferido, da largura de banda e da latência (Equação 4), e é reduzido por compressão, CDN e cache (Capítulo 4). O tempo de compilação é aproximadamente proporcional ao tamanho do código; os compiladores de base reduzem o atraso até a primeira execução, ao custo de código inicialmente menos eficiente, que é substituído quando o otimizador termina (BACKES, 2018). Para reduzir esse componente na origem, as cadeias de compilação oferecem otimização de tamanho (-Os, -Oz) e eliminação de código morto na ligação. O tempo de inicialização inclui a cópia de segmentos de dados para a memória, a execução de construtores globais C++ e a preparação do motor — etapas que, em jogos portados, podem envolver a montagem do sistema de arquivos virtual com centenas de megabytes de ativos.

          6.3Uso de CPU

          Na execução de pico, as principais fontes de sobrecarga do Wasm em relação ao nativo identificadas por Jangda et al. (2019) foram: maior número de instruções e de loads/stores, devido à alocação de registradores menos eficiente; desvios adicionais, decorrentes de verificações de segurança (estouro de pilha, chamadas indiretas); e maior ocupação de cache de instruções pesquisa anterior. Dois recursos ajudam a aproximar o desempenho do nativo em cargas paralelizáveis: as instruções SIMD de 128 bits, que processam vários valores por instrução (vetores de posições, matrizes de transformação, mistura de áudio), e as threads com memória compartilhada — esta última sujeita às restrições de isolamento discutidas na Seção 5.3.

          6.4Uso de memória

          O consumo total de memória de um jogo web pode ser estimado como:

          Mtotal ≈ Mlin + MJS + Mcód + MGPU + Máudio + Mnav
          (7)

          em que Mlin é a memória linear do módulo; MJS, o heap JavaScript (cola, objetos da página); Mcód, o código de máquina gerado; MGPU, texturas e buffers na memória de vídeo (Equação 2); Máudio, amostras PCM decodificadas; e Mnav, a sobrecarga fixa do próprio navegador.

          Duas particularidades merecem destaque. Primeiro, a memória linear só cresce: memória liberada por free() retorna ao alocador do programa, mas não ao sistema operacional, de modo que picos de uso tornam-se permanentes durante a sessão fato documentado. Segundo, ativos frequentemente existem em duplicidade — o arquivo comprimido no sistema de arquivos virtual (dentro da memória linear) e sua versão decodificada na GPU —, o que recomenda liberar os dados de origem após o envio à GPU interpretação do autor.

          6.5Frequência de quadros e tempo de quadro

          A métrica mais intuitiva é a taxa de quadros por segundo (FPS), mas sua média precisa ser calculada corretamente. Sendo Δti o tempo do i-ésimo quadro e N o número de quadros em uma janela de medição:

          FPSmédio = NΣi=1N Δti = 1Δt̄
          (8)

          A média aritmética dos FPS instantâneos (1/Δti) é sempre maior ou igual ao valor da Equação 8 (desigualdade entre médias aritmética e harmônica) e, por isso, superestima o desempenho quando há variação entre quadros.

          Exemplo didático hipotético

          Suponha 10 quadros: nove com 10 ms e um com 50 ms. A média dos FPS instantâneos seria (9 · 100 + 20) / 10 = 92 FPS. Pela Equação 8, o resultado correto é 10 / 0,140 s ≈ 71,4 FPS. O quadro de 50 ms — perceptível como um engasgo — praticamente desaparece da primeira média. Valores assumidos, não medidos.

          Por isso, análises de desempenho de jogos privilegiam a distribuição dos tempos de quadro: mediana, percentis altos (p95, p99) e a fração de quadros que excedem o orçamento (16,67 ms a 60 Hz; 8,33 ms a 120 Hz).

          6.6Latência de entrada e percentis

          A latência de entrada é o intervalo entre uma ação do jogador (tecla, toque, botão do controle) e a mudança correspondente na tela. No navegador, ela soma o tempo de entrega do evento pelo sistema e pelo navegador, a espera até o próximo quadro, o processamento no jogo, a renderização e a composição da página, além da latência do monitor. Como sua distribuição costuma ter cauda longa, deve ser descrita por percentis. Pelo método do posto mais próximo (nearest-rank), com as n observações ordenadas x(1) ≤ … ≤ x(n):

          Pp = x(⌈ p·n / 100 ⌉)
          (9)

          No exemplo anterior (n = 10), o p95 do tempo de quadro é x(10) = 50 ms, enquanto a mediana é 10 ms — o percentil captura o engasgo que a mediana ignora.

          6.7Gargalos de renderização

          Em jogos 3D, o gargalo frequentemente não está na lógica em Wasm, mas na submissão de trabalho à GPU. Cada chamada de desenho (draw call) e cada mudança de estado atravessam a cola JavaScript, a validação do navegador e a comunicação com o processo de GPU (Seções 2.1 e 5.3). Técnicas clássicas — agrupamento (batching), instanciamento (instancing), atlas de texturas e redução de trocas de estado — tornam-se ainda mais importantes na Web. O WebGPU foi projetado para reduzir parte dessa sobrecarga, com objetos de pipeline validados uma única vez e command buffers gravados antecipadamente (W3C, 2026a). A compilação de shaders é outro gargalo recorrente: shaders GLSL ou WGSL são traduzidos pelo navegador para a linguagem da API nativa subjacente, o que pode causar pausas na primeira vez que um material aparece em cena.

          6.8Gerenciamento de recursos

          Boas práticas incluem: alocar estruturas no início e reutilizá-las (pools), evitando crescimento da memória linear e, no lado JavaScript, pressão sobre o coletor de lixo; carregar recursos por demanda, com prioridade para o que está visível; liberar dados de origem após o envio à GPU; e usar formatos de textura comprimidos na GPU (Seção 4.5), que reduzem simultaneamente download, memória de vídeo e largura de banda de memória durante a renderização.

          6.9Dispositivos de baixo custo

          A promessa de democratização encontra seu teste mais duro em celulares e computadores de entrada. Nesses dispositivos, combinam-se CPUs mais lentas (maior tempo de compilação e de execução), pouca memória (limites de aba mais baixos e encerramento de abas em segundo plano), GPUs com menos largura de banda e redução de frequência por temperatura (thermal throttling) em sessões longas. Estratégias de mitigação incluem qualidade adaptativa (resolução de renderização dinâmica, níveis de detalhe), pacotes de ativos específicos por classe de dispositivo e a escolha de formatos suportados pela GPU móvel (ETC2/ASTC) interpretação do autor. Uma lacuna da literatura revisada é a escassez de estudos empíricos recentes de jogos Wasm completos em dispositivos de baixo custo — lacuna que o protocolo E2 procura endereçar.

          6.10Por que “próximo ao nativo” é possível, mas não garantido

          A síntese das evidências permite responder a essa questão de forma condicional. É possível porque: o Wasm é estaticamente tipado e validado, dispensando especulação; seu modelo de memória mapeia diretamente para instruções de load/store com verificações de limite muitas vezes delegadas ao hardware; e ele é compilado pelos mesmos tipos de back-ends otimizadores usados para código nativo. Não é garantido porque: a tradução final ocorre sob restrições de tempo de compilação no cliente; verificações de segurança adicionam instruções; recursos de hardware nem sempre estão expostos (vetores mais largos que 128 bits, por exemplo); threads dependem de condições de hospedagem; e o restante do sistema — API gráfica, áudio, entrada — opera por camadas de validação e comunicação entre processos que um jogo nativo não possui (HAAS et al., 2017; JANGDA et al., 2019) interpretação do autor.

          Análise

          Quatro padrões emergem dos dados. (i) Todos os binários Wasm se beneficiaram substancialmente da compressão sem perdas: a redução mínima foi de 49,7% (sql-wasm, zstd 3) e a máxima de 80,9% (esbuild, Brotli 11). (ii) Brotli 11 produziu o menor arquivo em todos os casos, com tamanhos 13,7% a 28,1% menores que os de gzip 9 (6,8 a 9,5 pontos percentuais de redução adicional). (iii) O nível do gzip foi praticamente irrelevante: entre os níveis 6 e 9, a diferença não passou de 0,2 ponto percentual — indicando que, para esses binários, o ganho de migrar de algoritmo é muito maior do que o de aumentar o nível. Em todos os casos, o binário mais compressível foi o produzido pelo compilador Go; uma possível explicação é a presença de metadados extensos do runtime da linguagem, hipótese não testada neste trabalho interpretação do autor.

          Somados, os sete binários Wasm totalizam 15.613.000 bytes; com gzip 9, seriam transferidos 4.668.223 bytes, e com Brotli 11, 3.460.742 bytes. Esses números referem-se exclusivamente ao código: o E1 não diz nada sobre ativos (texturas, áudio), cuja compressão ocorre no formato (Seção 4.5), nem sobre o tempo de descompressão no cliente (Equação 5). Para Zstandard, cabe notar que seu atrativo frequentemente citado é a velocidade de compressão e descompressão, aspecto não medido aqui.

          Um contraexemplo instrutivo

          O módulo de demonstração de 84 bytes (Seção 3.2), comprimido com gzip 9 no mesmo ambiente, resulta em 102 bytes — maior que o original, devido ao cabeçalho e ao rodapé fixos do formato gzip; com Brotli, resulta em 80 bytes experimento deste trabalho. Arquivos muito pequenos não se beneficiam de compressão, e servidores costumam definir um tamanho mínimo para aplicá-la.

          7.3Experimento E2 — protocolo para desempenho e tempo até a interação

          Estado do experimento

          O E2 não foi executado. Esta seção descreve o protocolo de forma completa e o código necessário para executá-lo. As tabelas de resultados permanecem vazias; qualquer valor nelas inserido no futuro deverá vir de execução real, com o ambiente documentado.

          Hipóteses

          • H1 — Para um núcleo de simulação física (N-corpos), a mediana do tempo de execução difere entre as versões JavaScript e WebAssembly. H10: as distribuições não diferem.
          • H2 — Sob rede restrita, a codificação HTTP (identity, gzip, Brotli, zstd) altera a mediana do tempo até o módulo estar pronto para execução. H20: não altera.
          • H3 — A codificação altera o tempo de transferência, mas não o tempo de compilação residual (após o término da transferência). H30: o tempo de compilação residual difere entre codificações.

          Carga de trabalho

          Uma simulação gravitacional de N-corpos com complexidade O(N²) por passo, implementada em C (nbody.c) e portada linha a linha para JavaScript (nbody.mjs), com o mesmo gerador pseudoaleatório e a mesma ordem de operações de ponto flutuante (Apêndice A). A escolha se justifica por ser representativa de núcleos de física de jogos e por permitir verificação de correção: ambas as versões devem produzir a mesma soma de verificação. Como teste preliminar de correção — não de desempenho —, a versão C compilada nativamente (gcc, -ffp-contract=off) e a versão JavaScript (Node.js) produziram a mesma soma de verificação, bit a bit, para N = 128 e 50 passos (12.071317837209453).

          Capítulo 8

          Segurança, limitações e desafios

          O WebAssembly protege o navegador do programa — não protege o programa de si mesmo, não esconde o código e não elimina os custos de distribuir conteúdo pesado.

          Pontos-chave do capítulo
          • Há duas camadas de isolamento: a semântica do Wasm e a sandbox de processos do navegador.
          • Código C/C++ inseguro continua inseguro dentro da memória linear, e pode até perder mitigações nativas.
          • Wasm não é ofuscação: binários podem ser desmontados e analisados; tudo que é enviado ao cliente pode ser extraído.
          • Limites de memória, de API gráfica, de acesso ao sistema e de custo de banda restringem o tipo de jogo viável.

          8.1Isolamento e sandbox

          A segurança de um jogo Wasm no navegador apoia-se em duas camadas complementares. A primeira é semântica: pela definição do formato, um módulo só acessa sua memória, suas tabelas e as funções importadas, e todo código é validado antes de executar (Seção 2.7) (HAAS et al., 2017). A segunda é a sandbox do navegador: mesmo que um erro no motor Wasm permitisse escapar da primeira camada, o código estaria confinado a um processo de renderização com privilégios mínimos (Seção 2.1). Ataques de execução especulativa, porém, mostraram que isolamento lógico não basta quando o código pode medir tempos com alta precisão (KOCHER et al., 2019). Como memória compartilhada entre threads permite construir temporizadores precisos, os navegadores condicionaram o SharedArrayBuffer ao isolamento de origem cruzada (MDN WEB DOCS, 2026a) — uma medida de segurança com consequências diretas para a arquitetura de jogos (Seção 5.3).

          8.2Limites de memória

          Memórias Wasm de 32 bits estão limitadas a 4 GiB pela própria largura dos endereços (HAAS; KUMMEROW; ZAKAI, 2020). Na prática, o limite efetivo pode ser bem menor: navegadores impõem tetos por aba, e sistemas móveis encerram abas que consomem muita memória. As memórias de 64 bits introduzidas no Wasm 3.0 ampliam o limite teórico, mas, na Web, cada memória de 64 bits está limitada a 16 GB (ROSSBERG, 2025), além de exigirem verificações de limite explícitas, já que a técnica de páginas de guarda usada para endereços de 32 bits não se aplica da mesma forma. Somam-se a isso a impossibilidade de reduzir a memória linear na especificação base e a duplicação de ativos entre memória linear e GPU (Seção 6.4).

          8.3Vulnerabilidades herdadas do código compilado

          Compilar C ou C++ para Wasm não corrige estouros de buffer, uso após liberação ou estouros de inteiros. Lehmann, Kinder e Pradel (2020) analisaram sistematicamente esse cenário e mostraram que, dentro da memória linear, faltam mitigações comuns em binários nativos modernos: não há páginas somente-leitura para proteger dados constantes, não há randomização do leiaute de memória, e a pilha sombra e o heap são vizinhos sem páginas de guarda entre si. Os autores demonstraram que uma corrupção de memória em um módulo pode ser explorada para sobrescrever dados usados em chamadas a funções importadas — e, por meio delas, causar efeitos fora do módulo, como injeção de código na página pesquisa anterior. Em estudo empírico com binários coletados de fontes reais, Hilbig, Lehmann e Pradel (2021) verificaram que a maioria havia sido compilada a partir de linguagens sem segurança de memória, como C e C++ — o que torna essas vulnerabilidades praticamente relevantes, e não apenas teóricas.

          Para jogos, as mitigações incluem: preferir linguagens com segurança de memória (Rust sem unsafe) para código novo; compilar com sanitizers durante o desenvolvimento; limitar ao mínimo as funções importadas com potencial perigoso (aquelas que interpretam strings como HTML ou código); e nunca confiar em dados vindos de fontes externas (níveis criados por usuários, mensagens de rede) sem validação.

          8.4Cadeia de dependências

          Um jogo web típico agrega o motor, bibliotecas C/C++ portadas, pacotes npm e crates Rust, além das próprias ferramentas de build. Cada elo pode ser comprometido. Como binários Wasm são opacos à revisão visual, uma dependência maliciosa pode passar despercebida com mais facilidade do que em código-fonte JavaScript legível. Boas práticas incluem fixar versões com arquivos de bloqueio (lockfiles), verificar hashes, manter um inventário de componentes (SBOM), preferir builds reproduzíveis e verificar a integridade dos recursos baixados — por exemplo, com o atributo integrity em <script> ou na opção homônima de fetch(), que rejeita respostas cujo hash não corresponda ao esperado (W3C, 2016). Os hashes SHA-256 registrados na Tabela 9 ilustram essa prática para os binários do E1.

          8.5Restrições de acesso ao sistema operacional

          Por projeto, jogos no navegador não acessam livremente o sistema de arquivos, não abrem sockets arbitrários (apenas HTTP, WebSocket, WebRTC e WebTransport), não instalam drivers nem componentes de núcleo e dependem de gestos do usuário para ações como iniciar áudio, entrar em tela cheia ou capturar o ponteiro. Para a maioria dos jogos, essas restrições são aceitáveis; para alguns, são impeditivas: sistemas antitrapaça que operam no núcleo do sistema operacional, por exemplo, são incompatíveis com o modelo de segurança da Web interpretação do autor.

          8.6Compatibilidade entre navegadores

          Embora o núcleo do Wasm seja universal, extensões (SIMD relaxado, coleta de lixo, exceções, memory64), APIs gráficas (WebGPU) e codificações (zstd) chegam aos navegadores em momentos diferentes. A prática recomendada é a detecção de recursos em tempo de execução — por exemplo, validar com WebAssembly.validate() um pequeno módulo que usa a instrução desejada — e a distribuição de variantes do binário, com e sem o recurso (MDN WEB DOCS, 2026b). Cada variante, porém, multiplica o esforço de teste e o volume de artefatos a manter em cache.

          8.7Limitações de GPU e de APIs gráficas

          O WebGL 2, base mais compatível, corresponde a um nível de funcionalidade do OpenGL ES 3.0 e não oferece compute shaders (KHRONOS GROUP, 2017). O WebGPU supre essa lacuna, mas sua especificação prioriza funcionalidades portáveis entre Vulkan, Metal e Direct3D 12 (W3C, 2026a); recursos de ponta disponíveis em APIs nativas — como aceleração de traçado de raios em hardware — não fazem parte da especificação vigente. Há ainda listas de bloqueio de drivers problemáticos mantidas pelos navegadores e a possibilidade de perda de contexto gráfico, que o jogo precisa tratar.

          8.8Download inicial de grandes volumes de recursos

          Jogos comerciais de grande porte ocupam dezenas de gigabytes. Mesmo com compressão eficiente, transferir esse volume a cada nova instalação, depender de cotas de armazenamento do navegador — que podem ser liberadas sob pressão de espaço — e manter tudo em cache local não é compatível com a proposta de “jogo instantâneo”. O navegador é mais adequado a jogos cujo caminho crítico caiba em poucas dezenas de megabytes e cujo conteúdo possa ser transmitido progressivamente (Seção 4.8) interpretação do autor.

          8.9Pirataria, distribuição de conteúdo e proteção de ativos

          Tudo o que um jogo web executa precisa ser entregue ao cliente — código e ativos. O formato binário do Wasm não é um mecanismo de proteção: ferramentas públicas, como as do WABT, convertem binários de volta ao formato texto e produzem pseudocódigo legível, e os ativos podem ser capturados nas ferramentas de desenvolvedor do navegador. A ofuscação eleva o custo da análise, mas não a impede. Por isso, as estratégias realistas de proteção são arquiteturais: manter lógica sensível (economia do jogo, validação de partidas, conteúdo pago) em servidores autoritativos, entregar conteúdo premium apenas após autenticação e aceitar que a parte executada no cliente é, em princípio, inspecionável interpretação do autor.

          8.10Custos de infraestrutura e manutenção

          Ao distribuir pela Web, o desenvolvedor assume o custo de transferência que, em lojas de aplicativos, é absorvido pela plataforma em troca de taxas. Um modelo simples para o custo de banda é:

          C ≈ Nv · (1 − h) · St · p
          (10)

          em que Nv é o número de visitas, h a fração atendida pelo cache local do navegador (visitas recorrentes sem novo download), St o tamanho transferido por visita sem cache e p o preço por unidade de dados da CDN.

          Exemplo didático hipotético

          Com 100.000 visitas sem cache (h = 0), 50 MB transferidos por visita e um preço assumido de US$ 0,05 por GB, o custo seria 100.000 · 50 MB = 5.000 GB → US$ 250. Se a compressão reduzir St em 25%, o custo cai proporcionalmente. O preço é arbitrário e não corresponde a nenhuma tabela comercial real.

          Somam-se custos de manutenção: acompanhar mudanças nos navegadores, testar múltiplas combinações de navegador e dispositivo, manter variantes de binários e cuidar da configuração do servidor (MIME correto, codificações, cabeçalhos de cache e de isolamento).

          Capítulo 9

          Aplicações reais e perspectivas futuras

          Motores, bibliotecas, emuladores e portes completos já existem. A questão é separar o que cabe ao Wasm do que cabe ao WebGL, ao WebGPU e à rede — e o que ainda é promessa.

          Pontos-chave do capítulo
          • Unity e Godot exportam para a Web com Wasm + WebGL 2; o Unity também oferece WebGPU como API opcional.
          • Física, decodificação de malhas e transcodificação de texturas já são entregues como módulos Wasm reutilizáveis.
          • Emuladores e portes como o de Doom 3 mostram motores nativos inteiros rodando no navegador.
          • Recursos futuros devem ser classificados: disponível, disponível com restrições, experimental ou proposta.
          • O navegador não é a melhor plataforma para todo jogo: AAA de dezenas de GB, antitrapaça de núcleo e recursos gráficos de ponta seguem nativos.

          9.1Motores de jogos

          O Unity oferece a plataforma de compilação “Web”, que converte o código do motor e os scripts C# do projeto (via IL2CPP, que gera C++) em WebAssembly com a cadeia Emscripten, e renderiza com WebGL 2; a documentação do Unity 6 apresenta o WebGPU como API gráfica adicional, que precisa ser habilitada manualmente, ao passo que o WebGL 2 vem habilitado por padrão (UNITY TECHNOLOGIES, 2026; UNITY TECHNOLOGIES, 2026b). O Godot exporta projetos para a Web compilando o motor C++ para Wasm com Emscripten e renderizando com WebGL 2; como discutido na Seção 5.3, a versão 4.3 reintroduziu exportações de thread única para facilitar a hospedagem (GODOT ENGINE, 2026; SCOTT, 2024). Nos dois casos, é importante atribuir corretamente as responsabilidades: o Wasm executa o motor e a lógica; a renderização depende do WebGL ou do WebGPU; o áudio, da Web Audio; e a viabilidade de threads, dos cabeçalhos do servidor.

          9.2Bibliotecas de física e de processamento de conteúdo

          Um uso talvez menos visível, mas muito difundido, é a distribuição de componentes de motor como módulos Wasm independentes, consumidos por motores e bibliotecas JavaScript. Os binários avaliados no E1 exemplificam esse padrão: o Box2D (física 2D) e o Bullet, via ammo.js (física 3D), compilados de C++ com Emscripten; o Rapier (física 3D), escrito em Rust; e o decodificador Draco e o transcodificador Basis Universal, distribuídos junto com a biblioteca three.js para carregar malhas e texturas comprimidas (BIRCH, 2026; DIMFORGE, 2026; THREE.JS AUTHORS, 2026). Esse padrão híbrido — renderização e orquestração em JavaScript, núcleos computacionais em Wasm — explora exatamente os pontos fortes discutidos na Seção 3.7, com baixo número de cruzamentos de fronteira por quadro.

          9.3Emuladores e portes completos

          Emuladores são um caso de uso natural, por serem programas nativos computacionalmente intensivos com interfaces simples. O js-dos executa jogos de MS-DOS no navegador com os emuladores DOSBox e DOSBox-X, em versões WebAssembly e JavaScript puro (JS-DOS, 2026). Um exemplo de porte de motor 3D comercial é o d3wasm, que adapta o id Tech 4 — o motor de Doom 3, a partir do projeto de código aberto dhewm3 — para WebAssembly e WebGL usando Emscripten (CUVILLIER, 2019). Casos assim são valiosos como demonstrações de viabilidade, mas não devem ser generalizados: jogos antigos têm conjuntos de ativos pequenos para os padrões atuais e exigências gráficas compatíveis com o WebGL interpretação do autor.

          9.4Ferramentas interativas e computação no cliente

          Fora dos jogos, Wasm viabiliza bancos de dados no navegador (SQLite, via sql.js, incluído no E1 como controle), empacotadores de código (esbuild) e inferência de modelos de aprendizado de máquina. Neste último caso, bibliotecas como ONNX Runtime e Transformers.js já empregam o WebGPU para computação acelerada no navegador (BEAUFORT, 2025) — mais um exemplo de que a aceleração relevante pode vir da API de GPU, e não do Wasm em si.

          9.6Potencial: jogos instantâneos, nuvem, multiplataforma e educação

          Jogos instantâneos. A URL como unidade de distribuição permite compartilhar um jogo em uma mensagem, incorporá-lo em uma página e oferecer demonstrações sem instalação. O custo de experimentar cai a quase zero para o jogador.

          Jogos em nuvem. É útil distinguir dois paradigmas. No cloud gaming, o jogo roda em um servidor e o navegador recebe vídeo e envia entradas; o cliente é leve, mas a experiência depende de rede com baixa latência e largura de banda contínua, e o custo computacional recai sobre o provedor. Com Wasm, o jogo roda no dispositivo do jogador: a rede é necessária para a carga inicial, mas não durante a partida (salvo em multijogador), e o custo computacional é do cliente. Os paradigmas são complementares — o primeiro favorece jogos pesados em dispositivos fracos; o segundo, jogos leves e médios com resposta local imediata interpretação do autor.

          Distribuição multiplataforma. Um único build atende Windows, macOS, Linux, ChromeOS e, com ressalvas de desempenho e de controles, dispositivos móveis, eliminando a necessidade de binários por sistema e arquitetura (Seção 2.5).

          Experiências educacionais e democratização. Em laboratórios escolares com máquinas gerenciadas, onde instalar software exige intervenção administrativa, um jogo educativo acessível por URL remove uma barreira prática. A democratização, entretanto, é condicional: depende de conectividade para a carga inicial, de hardware minimamente capaz e de jogos projetados com caminho crítico enxuto e qualidade adaptativa (Seção 6.9).

          9.7Quando o navegador não é a melhor plataforma

          Com base na análise precedente, identificam-se cenários em que a execução nativa tende a ser preferível interpretação do autor:

          • jogos com dezenas de gigabytes de ativos, cuja transferência e armazenamento conflitam com cotas e com a expectativa de acesso imediato (Seção 8.8);
          • jogos que exigem recursos gráficos ausentes das APIs web, como traçado de raios por hardware (Seção 8.7);
          • jogos competitivos que dependem de antitrapaça no núcleo do sistema ou de latência de entrada mínima e taxas de quadros muito altas (Seções 6.6 e 8.5);
          • motores intensamente multithread distribuídos em plataformas que não permitem configurar COOP/COEP (Seção 5.3);
          • projetos em que a proteção de propriedade intelectual no cliente é requisito contratual (Seção 8.9).

          Discussão dos resultados

          Pontos-chave do capítulo

          10.1Síntese das evidências

          As evidências reunidas têm três naturezas. Os fatos documentados — especificações e documentação oficial — estabelecem o que o WebAssembly é e o que as plataformas permitem: um formato validável, isolado, portátil, compilado no cliente e dependente de importações para qualquer interação externa. As pesquisas anteriores quantificam, em condições específicas, o desempenho e a segurança: proximidade do nativo em núcleos compactos, sobrecarga média de 45% a 55% em programas grandes nas versões avaliadas por Jangda et al. (2019), e vulnerabilidades de memória exploráveis dentro da sandbox (LEHMANN; KINDER; PRADEL, 2020). O experimento deste trabalho (E1) acrescenta dados primários sobre o tamanho transferido de binários reais, mostrando que a codificação HTTP reduz pela metade ou mais o código a ser baixado, e que a escolha do algoritmo importa mais do que a do nível.

          10.3Avaliação da hipótese de trabalho

          A hipótese formulada na Seção 1.4 afirmava que o WebAssembly é condição necessária, mas não suficiente, para a viabilidade de jogos complexos no navegador, e que a experiência final depende predominantemente de fatores externos ao Wasm. As evidências convergem para sustentá-la. A necessidade decorre de que nenhuma outra tecnologia padronizada permite reutilizar motores C/C++ com desempenho próximo ao nativo — o asm.js, seu antecessor, foi superado justamente pelo Wasm (HAAS et al., 2017). A insuficiência aparece em cada capítulo: o E1 mostrou que a redução do código transferido depende da codificação HTTP, e não do formato; o Capítulo 4 mostrou que os ativos — tipicamente a maior parte do download — são comprimidos por formatos independentes do Wasm; o Capítulo 5, que gráficos, áudio e threads dependem de outras APIs e da configuração do servidor; e o Capítulo 6, que o tempo até a interação é uma soma de componentes, dos quais a execução do Wasm é apenas um interpretação do autor.

          Ressalva-se que essa avaliação é qualitativa: a parte de desempenho repousa em estudos de terceiros, realizados com versões de navegadores anteriores às atuais, e o E2, que permitiria testar H1–H3 quantitativamente, não foi executado. A hipótese é, portanto, sustentada pelas evidências disponíveis, e não demonstrada experimentalmente em sua totalidade.

          10.4Vantagens, desvantagens e benefícios condicionais

          Vantagens

          Acesso por URL, sem instalação; um único build para todas as plataformas; reuso de código C/C++/Rust; execução eficiente de núcleos numéricos; isolamento forte em relação ao sistema; atualizações transparentes.

          Desvantagens

          Sobrecarga mensurável frente ao nativo em programas grandes; compilação no cliente; limites de memória e de API gráfica; restrições de acesso ao sistema; código inspecionável; custo de banda assumido pelo desenvolvedor.

          Benefícios condicionais

          Carregamento rápido (se houver compressão, cache e caminho crítico enxuto); paralelismo (se a hospedagem permitir COOP/COEP); gráficos modernos (se WebGPU estiver disponível); democratização (se o dispositivo e a conexão forem suficientes).

          Esse quadro desloca a pergunta de “o WebAssembly é bom para jogos?” para “sob que condições de engenharia e de público um determinado jogo é viável no navegador?”. A resposta depende do tamanho do conteúdo, das exigências gráficas, do público-alvo e da infraestrutura de distribuição — e não apenas da tecnologia de execução.

          Sobre previsões

          As perspectivas discutidas no Capítulo 9 (maturação do WebGPU, threads mais flexíveis, dicionários de compressão, convergência cliente-servidor via WASI) são tendências plausíveis à luz do estado dos padrões, mas não fatos comprovados. Sua concretização depende de decisões de implementação dos navegadores, de adoção pela indústria e de fatores econômicos fora do escopo deste trabalho.

          Capítulo 11

          Conclusão

          Desmontada camada por camada, a “magia programacional” revela-se engenharia — o que a torna menos misteriosa e mais admirável.

          Pontos-chave do capítulo
          • WebAssembly viabiliza jogos no navegador em medida considerável, mas condicionada a compressão, formatos de ativos, cache e APIs gráficas.
          • Contribuições: modelo integrado de análise, medição real de compressão (E1), protocolo reproduzível (E2) e documento interativo.
          • Trabalhos futuros: executar o E2, estudar jogos completos em dispositivos de baixo custo e avaliar dicionários de compressão.

          11.1Resposta ao problema de pesquisa

          Este trabalho perguntou em que medida o WebAssembly, combinado com técnicas modernas de compressão, compilação e distribuição, pode viabilizar a execução de jogos complexos diretamente em navegadores, reduzindo barreiras de instalação, compatibilidade e acesso sem comprometer excessivamente o desempenho e a experiência. A resposta construída é a de uma viabilidade ampla, porém condicionada. O WebAssembly remove a barreira da instalação e da compatibilidade entre sistemas e arquiteturas, e permite reutilizar motores nativos com desempenho que, em núcleos computacionais, pode se aproximar do nativo. Contudo, a experiência final depende de forma decisiva de elementos externos a ele: da codificação HTTP, que no E1 reduziu os binários reais em 58% a 81% com Brotli 11; dos formatos de ativos, que determinam tanto o download quanto a memória ocupada; do cache e do carregamento progressivo, que governam o tempo até a interação; das APIs gráficas, cuja disponibilidade moderna (WebGPU) ainda é desigual; e da configuração do servidor, da qual depende até mesmo o uso de threads. Para jogos de porte pequeno e médio, cujo caminho crítico cabe em dezenas de megabytes, a combinação dessas técnicas permite experiências próximas às de aplicações instaladas. Para jogos de grande porte, com dezenas de gigabytes e exigências gráficas de ponta, o navegador permanece uma plataforma complementar, e não substituta.

          11.2Contribuições

          1. Modelo integrado de análise, que articula compilação, compressão, transferência, compilação no cliente, inicialização e renderização (Equação 6 e Figura 11), em vez de tratar desempenho de execução ou tamanho de download isoladamente.
          2. Dados primários reproduzíveis sobre a compressão de sete binários Wasm reais com seis tratamentos (E1), incluindo versões fixadas, hashes e script.
          3. Protocolo experimental completo (E2), com código verificado quanto à equivalência entre as implementações C e JavaScript, plano estatístico robusto e análise de ameaças à validade.
          4. Distinção sistemática entre níveis de evidência, aplicada ao longo de todo o texto, separando fatos documentados, resultados de terceiros, dados próprios, exemplos hipotéticos e interpretações.
          5. Documento interativo que demonstra, no próprio navegador do leitor, o ciclo de vida de um módulo Wasm e o efeito da compressão — tornando o objeto de estudo parte da apresentação.

          11.3Limitações do trabalho

          (a) A análise de desempenho baseia-se em estudos de terceiros com versões de navegadores de 2017 a 2021, que não refletem necessariamente os motores atuais. (b) O E1 mede apenas tamanho, com uma amostra de conveniência de sete binários e as bibliotecas do Node.js. (c) O E2 não foi executado. (d) Não foi estudado um jogo completo com GPU, áudio e entrada em condições reais. (e) O estado de implementação de recursos foi verificado até outubro de 2026 e pode se alterar rapidamente.

          11.4Trabalhos futuros

          • Executar o protocolo E2 em múltiplos navegadores e dispositivos, incluindo celulares de entrada, e publicar os dados brutos.
          • Propor um E3 com um jogo completo exportado por Unity ou Godot, medindo tempo até a interação, distribuição de tempos de quadro e memória em redes reais.
          • Medir o tempo de descompressão de gzip, Brotli e zstd no cliente, completando a análise de custo-benefício da Equação 5.
          • Avaliar o transporte de dicionários de compressão (RFC 9842) para atualizações incrementais de binários de jogos.
          • Comparar WebGL 2 e WebGPU em um mesmo motor, isolando a sobrecarga de submissão de comandos.
          • Investigar o compartilhamento de módulos de lógica entre cliente (navegador) e servidor (WASI) em jogos multijogador autoritativos.

          11.5Considerações finais: a mágica desmontada

          O trabalho começou com uma metáfora: a de que o WebAssembly pareceria uma espécie de mágica programacional, capaz de transformar um programa nativo em uma experiência acessível por um link. Ao fim do percurso, a metáfora pode ser desmontada sem perder seu encanto. O truque tem nome e endereço. Está no compilador, que traduz C, C++ e Rust para uma representação portátil; no formato binário, desenhado para ser validado em uma única passagem e compilado enquanto ainda chega pela rede; no navegador, que isola o código, traduz cada função para o processador local e faz a ponte com a GPU; nos protocolos HTTP, que negociam a compressão e permitem armazenar o jogo em cache; nos formatos de textura, malha e áudio, que decidem quanto pesa cada mundo virtual; e na engenharia de software que costura tudo isso em um laço que precisa terminar a cada dezesseis milissegundos.

          Não há mágica — há integração. E é justamente porque cada camada pode ser explicada, medida e melhorada que essa integração representa uma via concreta para democratizar o acesso aos jogos.

          #include <math.h>
#ifdef __EMSCRIPTEN__
#include <emscripten/emscripten.h>
#else
#define EMSCRIPTEN_KEEPALIVE
#endif
#define MAXN 4096
static double px[MAXN], py[MAXN], pz[MAXN], vx[MAXN], vy[MAXN], vz[MAXN], m[MAXN];
static unsigned int seed;
static double rnd(void) { seed = seed * 1664525u + 1013904223u; return (seed >> 8) / 16777216.0; }

EMSCRIPTEN_KEEPALIVE
double simulate(int n, int steps) {
  if (n > MAXN) n = MAXN;
  seed = 42u;
  for (int i = 0; i < n; i++) {
    px[i] = rnd() * 2 - 1; py[i] = rnd() * 2 - 1; pz[i] = rnd() * 2 - 1;
    vx[i] = vy[i] = vz[i] = 0; m[i] = 0.5 + rnd();
  }
  const double dt = 1e-3, eps2 = 1e-4;
  for (int s = 0; s < steps; s++) {
    for (int i = 0; i < n; i++) {
      double ax = 0, ay = 0, az = 0;
      for (int j = 0; j < n; j++) {
        double dx = px[j] - px[i], dy = py[j] - py[i], dz = pz[j] - pz[i];
        double d2 = dx * dx + dy * dy + dz * dz + eps2;
        double inv = 1.0 / (d2 * sqrt(d2));
        ax += m[j] * dx * inv; ay += m[j] * dy * inv; az += m[j] * dz * inv;
      }
      vx[i] += ax * dt; vy[i] += ay * dt; vz[i] += az * dt;
    }
    for (int i = 0; i < n; i++) { px[i] += vx[i] * dt; py[i] += vy[i] * dt; pz[i] += vz[i] * dt; }
  }
  double c = 0;
  for (int i = 0; i < n; i++) c += px[i] + py[i] + pz[i];
  return c;
}

          """analyze.py — análise estatística do Experimento E2.

import sys
import numpy as np
import pandas as pd
from scipy.stats import mannwhitneyu

rng = np.random.default_rng(2026)

def boot_ci_median_ratio(a, b, n_boot=10_000, alpha=0.05):
    """IC por bootstrap percentil para a razão das medianas a/b."""
    a, b = np.asarray(a), np.asarray(b)
    ra = rng.choice(a, (n_boot, a.size), replace=True)
    rb = rng.choice(b, (n_boot, b.size), replace=True)
    ratios = np.median(ra, axis=1) / np.median(rb, axis=1)
    return np.quantile(ratios, [alpha / 2, 1 - alpha / 2])

def cliffs_delta(a, b):
    a, b = np.asarray(a)[:, None], np.asarray(b)[None, :]
    return float((a > b).mean() - (a < b).mean())

def holm(pvals):
    """Correção de Holm-Bonferroni; devolve p-valores ajustados na ordem original."""
    p = np.asarray(pvals); order = np.argsort(p); m = len(p)
    adj = np.empty(m); running = 0.0
    for k, idx in enumerate(order):
        running = max(running, min(1.0, (m - k) * p[idx]))
        adj[idx] = running
    return adj

raw = pd.read_csv(sys.argv[1])

# reduz-se cada repetição a uma observação: ready_ms é único; exec_ms vira a mediana das 10 medições.

          .agg(n=('rep', 'count'),
               ready_med=('ready_ms', 'median'),

          Glossário

          ABI (Application Binary Interface)
          Convenção que define como funções compiladas trocam dados em nível binário (registradores, pilha, leiaute de memória).
          AOT (Ahead-of-Time)
          Compilação realizada antes da execução e da distribuição do programa.
          ASTC / BCn / ETC2
          Famílias de formatos de compressão de textura em bloco decodificados diretamente pela GPU; ASTC e ETC2 predominam em dispositivos móveis, BCn em desktop.
          Asyncify
          Transformação do Binaryen que permite a código síncrono pausar e retomar a execução, ao custo de tamanho e velocidade.
          Basis Universal
          Formato de supercompressão de texturas que pode ser transcodificado no cliente para o formato suportado pela GPU local.
          Binaryen
          Biblioteca e conjunto de ferramentas de compilação para WebAssembly, que inclui o otimizador wasm-opt.
          Brotli
          Algoritmo de compressão sem perdas (RFC 7932) que combina LZ77, Huffman, modelagem de contexto e dicionário estático.
          Bytecode
          Representação intermediária compacta, executada por um interpretador ou traduzida para código de máquina.
          Cache imutável
          Estratégia em que arquivos com nome derivado do conteúdo são armazenados por longo prazo, sem revalidação.
          CDN
          Rede de servidores distribuídos geograficamente que entrega conteúdo a partir do ponto mais próximo do usuário.
          Código de cola (glue code)
          JavaScript gerado por ferramentas como Emscripten para implementar as importações de um módulo Wasm.
          COOP / COEP
          Cabeçalhos HTTP que, combinados, colocam a página em isolamento de origem cruzada, requisito para SharedArrayBuffer.
          DEFLATE
          Algoritmo de compressão (RFC 1951) que combina LZ77 e códigos de Huffman; base do gzip.
          Desotimização
          Retorno de código otimizado especulativamente para um nível menos otimizado quando uma suposição se mostra falsa.
          Draco
          Biblioteca de compressão de malhas 3D por quantização e codificação preditiva.
          Emscripten
          Cadeia de ferramentas que compila C e C++ para WebAssembly e gera bibliotecas de suporte e código de cola.
          Entropia
          Medida, em bits por símbolo, da informação média de uma fonte; limite inferior para compressão sem perdas.
          glTF
          Formato do Khronos Group para transmissão eficiente de cenas e modelos 3D.
          Instanciação
          Etapa que vincula um módulo Wasm compilado às suas importações e aloca memória, tabelas e globais.
          JIT (Just-in-Time)
          Compilação para código de máquina realizada durante a execução do programa.
          JSPI
          Proposta de integração entre WebAssembly e Promises do JavaScript, que permite suspender código Wasm enquanto aguarda operações assíncronas.
          KTX 2.0
          Contêiner do Khronos Group para texturas, com suporte a supercompressão Basis Universal.
          LEB128
          Codificação de inteiros de comprimento variável usada no formato binário do Wasm.
          LLVM
          Infraestrutura de compilação baseada em uma representação intermediária e em otimizações independentes de linguagem e arquitetura.
          Memória linear
          Vetor contíguo de bytes, endereçado a partir de zero, que serve de memória para programas Wasm; cresce em páginas de 64 KiB.
          Mipmap
          Sequência de versões reduzidas de uma textura usada para amostragem eficiente à distância.
          Módulo
          Unidade de distribuição e compilação do WebAssembly, composta por seções tipadas.
          OPFS
          Origin Private File System: sistema de arquivos privado de cada origem, definido pelo padrão File System do WHATWG.
          Percentil
          Valor abaixo do qual se encontra uma dada porcentagem das observações (por exemplo, p95).
          Sandbox
          Ambiente de execução isolado e com privilégios restritos.
          SharedArrayBuffer
          Buffer de memória compartilhável entre threads (Web Workers) do JavaScript.
          SIMD
          Instruções que operam sobre vários dados simultaneamente; no Wasm, vetores de 128 bits.
          Streaming compilation
          Compilação de um módulo Wasm enquanto seus bytes ainda estão sendo recebidos pela rede.
          Tempo até a interação (TTI)
          Intervalo entre o acesso à URL e o momento em que o jogo responde ao jogador.
          Trap
          Interrupção da execução Wasm causada por erro, como acesso fora dos limites da memória.
          Validação
          Verificação estática de que um módulo Wasm é bem formado e corretamente tipado, antes de qualquer execução.
          WASI
          WebAssembly System Interface: conjunto de interfaces padronizadas para executar Wasm fora do navegador.
          WAT
          WebAssembly Text Format: representação textual legível do formato binário.
          WebGL
          API gráfica web baseada no OpenGL ES; a versão 2.0 corresponde ao OpenGL ES 3.0.
          WebGPU
          API web moderna para gráficos e computação na GPU, com shaders em WGSL.
          Web Worker
          Mecanismo para executar scripts em threads separadas da thread principal da página.
          Zstandard (zstd)
          Algoritmo de compressão sem perdas (RFC 8878), suportado como codificação HTTP.
